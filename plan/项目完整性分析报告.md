## 一、项目现状概览

BabyStar 是一款面向新生儿家庭的护理记录 PWA 应用，技术栈为 Vue 3 + Vite + TypeScript + Vant 4 + Pinia + TailwindCSS v4（前端）和 Fastify + Prisma + PostgreSQL（后端）。

| 维度     | 现状                                                                                                  |
| -------- | ----------------------------------------------------------------------------------------------------- |
| 前端页面 | 9 个路由页面（登录、注册、首页、统计、档案、创建档案、家庭、加入家庭、成长记录）                      |
| 后端接口 | 34 个 REST API 端点，覆盖 7 个业务模块                                                                |
| 数据模型 | 7 张表（User、RefreshToken、Baby、BabyMember、InviteCode、CareRecord、GrowthRecord）                  |
| 核心功能 | 五类记录（奶粉/母乳/拉尿/拉屎/睡眠）、每日统计、成长曲线、宝宝档案、家庭协作、离线暂存、深色模式、PWA |
| 单元测试 | 前后端合计 6 个测试文件、78 条用例全部通过                                                            |

**整体评价：核心记录闭环、睡眠维度、成长曲线、深色主题均已上线，产品已进入"记录维度完整、数据初具价值"的阶段。剩余短板集中在历史趋势图表、数据导出、喂养提醒等运营/留存能力，以及生产环境部署与错误监控等基础设施。**

## 三、缺失功能分析

### 3.1 P0 — 必须补齐（直接影响留存和核心价值）

#### 3.1.1 历史趋势与图表（护理记录）

**缺失原因**：后端已有 `/stats/range` 接口支持日期范围查询，但前端只在成长记录里使用了 ECharts，护理记录（奶粉/母乳/尿/便/睡眠）仍只有逐日翻看。

**业务价值**：用户最关心的问题是"宝宝吃得够不够""排泄是否正常""这个星期和上个星期比怎么样"。只有单日数据无法回答这些问题，用户需要看到趋势才能建立信心。

**建议方案**：

- 统计页新增"周视图/月视图"切换 Tab（复用现有 ECharts 依赖）
- 折线图：每日奶量、母乳时长、睡眠时长趋势
- 柱状图：每日拉尿/拉屎次数
- 周报摘要卡片：本周总奶量、日均喂奶次数、日均睡眠、与上周对比箭头

**预估工期**：5-7 天

#### 3.1.2 数据导出

**缺失原因**：档案页的"导出数据"按钮已存在但显示"即将开放"，功能未实现。

**业务价值**：用户带宝宝看儿科医生时，经常需要展示喂养记录。一份清晰的数据报告是 BabyStar 区别于纸笔记录的核心卖点之一。同时《个人信息保护法》要求提供数据可携带权。

**建议方案**：

- 短期：导出 CSV，包含护理记录与成长记录明细
- 中期：生成可分享的长图（近期喂养/排泄/睡眠汇总 + 成长曲线截图）
- 长期：PDF 报告，可直接发给医生

**预估工期**：3-5 天（CSV 先行），5-7 天（含图片报告）

#### 3.1.3 HTTPS / 生产部署

**缺失原因**：当前仅在本地开发运行，PWA + Service Worker + `Notification` 都要求 HTTPS。

**建议方案**：

- 后端 Dockerfile + Compose 一键部署
- Nginx 反向代理 + Let's Encrypt 证书
- 前端产物由 CDN 或 Nginx 托管
- 环境变量分离 `.env.production`

**预估工期**：3-5 天

### 3.2 P1 — 应当规划（提升产品体验和竞争力）

#### 3.2.1 喂养/用药提醒

**业务价值**：新生儿喂养间隔通常 2-3 小时，新手父母容易忘记或焦虑。计时器只能被动展示"已过多久"，不能主动提醒"该喂了"。

**建议方案**：

- 基于上次喂奶时间 + 用户设置的间隔（默认 3 小时），到时间后发送 PWA 通知
- 需要 Notification API 权限申请 + Service Worker push
- 设置页新增提醒间隔配置（喂养、维生素 AD/D 每日提醒共用）

**预估工期**：3-5 天

#### 3.2.2 记录回填（历史时间补录）

**业务价值**：照顾新生儿时手忙脚乱，经常忘记及时记录。当前奶粉/母乳/尿/便仍只能记录当前时间，只有睡眠支持手动补录。

**建议方案**：

- 记录对话框中统一增加时间选择器（默认当前时间，可往前调）
- 统计页允许从某天直接"新增记录"并指定时间
- 回填的记录在列表中用虚线边框或标记区分

**预估工期**：2-3 天

#### 3.2.3 体温记录

**业务价值**：新生儿体温监测是重要的健康指标，尤其前 3 个月。

**建议方案**：

- 新增 `temperature` 到 CareEventType
- 记录字段：体温值（35.0-42.0°C）、测量方式（耳温/额温/肛温）
- 统计页增加体温卡片，异常值（≥37.5°C）红色高亮

**预估工期**：2-3 天

#### 3.2.4 用药/维生素记录

**业务价值**：新生儿需要每日补充维生素 AD/D，交替服用。这是日常刚需记录项。

**建议方案**：

- 新增 `medication` 到 CareEventType
- 记录字段：药品名称（预设：维生素 AD、维生素 D、其他）、剂量、备注
- 与喂养提醒共用提醒中心

**预估工期**：2-3 天

#### 3.2.5 文件上传服务

**业务价值**：当前头像以 Base64 存储，无法跨设备同步、占用空间大、影响接口性能。

**建议方案**：

- 后端集成 `@fastify/multipart`
- 可接入 OSS（阿里云 OSS、腾讯云 COS）或本地存储
- 头像 URL 替换为文件访问地址
- 后续支持里程碑/日记的图片附件

**预估工期**：2-3 天

#### 3.2.6 错误监控与运营基础设施

**业务价值**：线上问题无法感知，用户流失原因不可分析。

**建议方案**：

- 前后端接入 Sentry（或自建方案）
- 数据库定时备份脚本
- 后端结构化日志（Pino JSON）+ 集中查看
- 简易性能监控：接口响应时间、页面加载 P95

**预估工期**：3-5 天

### 3.3 P2 — 值得建设（增强产品深度和差异化）

#### 3.3.1 里程碑记录

**业务价值**：第一次微笑、第一次翻身、第一声"妈妈"——这些瞬间是父母最珍贵的记忆，也是发育评估的重要参考。

**建议方案**：

- 新增里程碑页面，按类别分组（大运动、精细运动、语言、社交）
- 每个里程碑预设列表 + 自定义添加
- 记录达成日期 + 可选照片（依赖 3.2.5 的文件上传）
- 时间线展示

**预估工期**：3-4 天

#### 3.3.2 深度统计与分析

**业务价值**：超越"今天记了多少"，回答"宝宝的作息规律吗""和同龄宝宝比怎么样"。

**建议方案**：

- 喂养效率分析：日均奶量/喂奶次数随月龄的变化趋势
- 作息规律度：喂奶-清醒-睡眠的周期可视化（结合已有睡眠数据）
- 同龄对比（需足够数据量支撑，可后期考虑）

**预估工期**：5-7 天

#### 3.3.3 通知中心 & 家庭成员动态

**业务价值**：家庭成员之间的协作需要信息同步——"宝宝刚吃了奶""今天拉了 3 次"。

**建议方案**：

- 其他成员记录时推送通知给所有家庭成员
- 应用内消息列表，展示家庭成员的动态
- 需要后端 WebSocket 或轮询机制

**预估工期**：5-7 天

#### 3.3.4 CI/CD 与 E2E 测试

**建议方案**：

- GitHub Actions（或 Gitea Actions / Jenkins）流水线：install → lint → test → build → deploy
- 前端 Playwright E2E 覆盖关键路径：登录 → 建档 → 记录 → 统计 → 家庭协作
- 引入 ESLint + Prettier 统一规范

**预估工期**：5-7 天

## 七、总结

BabyStar 已经从"能用"迈入"好用"的门槛：五类核心护理记录 + 成长曲线补齐了记录维度，睡眠计时和清醒窗口回应了新生儿家庭最刚需的观察点，深色模式贴合夜间喂奶场景，单元测试基线让工程可持续演进。

当前最大的短板已经不在"功能维度"，而在**数据消费层**（护理趋势图表、导出、周报）和**运营基础设施**（HTTPS 部署、错误监控、CI/CD）。用户每天辛苦录入的数据只有变成"可翻阅的趋势"和"可分享的报告"，才能真正沉淀成 BabyStar 的护城河。

下一步应优先补齐 **历史趋势图表 + 数据导出 + HTTPS 部署** 三件事——它们分别解决"能看到""能带走""能上线"三个当下最直接的堵点，也是从"内测可用"迈向"正式发布"的关键三步。
